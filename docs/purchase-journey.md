# FlowerStudio：商家与购买流程讨论稿

状态：最终产品方向已明确，交易方式和上线范围尚待验证。

日期：2026-10-12

关联：[功能模块](functional-modules.md)、[UI 方案](ui-plan.md)、[写实视觉路线](visual-strategy.md)。

## 1. 本轮已确认与未确认的事项

已确认：

- 用户认可现有 UI 的总体布局。具体入口偏好与局部控件仍可继续调整。
- 最终花材呈现应写实，视觉技术路线通过样片对比决定。
- FlowerStudio 的最终形态需要让设计与商家购买相连接。

未确认：

- FlowerStudio 内统一下单，或通过已有商家页面完成交易。
- 接入美团等平台的具体方式、业务范围与申请资格。
- 商家合作、报价、支付、履约与售后的责任安排。

第一版仍按此前确认的设计与采购清单推进。最终购买流程指导数据与模块边界，不据此提前建设全部交易系统。

按现有项目定位，采购以在家 DIY 所需原始花材为主。商家按设计制作成品可作为另一个服务讨论，不默认纳入首版。

## 2. 最终用户流程

选择灵感 / 自由设计
→ 写实预览与编辑
→ 确认花材配方
→ 查看可购买方案
→ 确认商家、数量、替代项与报价
→ 通过选定渠道购买
→ 商家备货与配送
→ 收到花材，在家完成作品。

最终目标需要同时验证视觉效果、花材可采购性与商家履约能力。

## 3. 设计、供货与购买需要区分

| 层次 | 拥有的信息 | 举例 |
| --- | --- | --- |
| 设计花材 | 品种、颜色、规格、采购单位与设计用量 | 白玫瑰 4 支 |
| 商家供货商品 | 商家、商品标识、实际规格、售卖单位、最低数量、供货信息 | 某商家白玫瑰，每份 5 支 |
| 购买方案 | 覆盖的需求、实际购买数量、缺货与替代、报价及渠道 | 购买 1 份，共 5 支，其中 4 支用于设计 |
| 交易记录 | 经确认的购买快照、付款和履约状态 | 外部渠道订单，或未来平台内订单 |

必须明确设计用量与实际购买数量。商家按扎、份或束销售时，不能直接把画布中的支数当作购买份数。

一个设计花材可对应多个商家的供货商品。设计本身不绑定某一家商家的商品标识。

价格、库存、配送范围与更新时间属于供货及报价信息，不应写成花种本身的固定属性。

## 4. 三种候选购买方式

### 方式 A：商家页面跳转

平台生成清单，展示已核验的商家店铺或商品入口；用户前往商家渠道购买。

需要验证：

- 店铺或商品链接能否在目标手机与浏览器中正常打开。
- 用户是否能找到清单所需品种、颜色和数量。
- 是否有获准的渠道能力传递清单、商品或数量。
- 是否有授权的成交反馈或归因方式。

初期可以人工维护合作商家链接。打开店铺、打开单品、一次带入多个商品、自动建单是不同能力，不能因一个链接可打开而默认其他能力成立。

若无法获得订单反馈，平台只能记录跳转或用户主动反馈，不能将点击当作成交。

### 方式 B：采购需求单与人工确认（试点建议）

用户提交设计快照及花材清单，由合作花店确认能否按需供货、替代项、实际购买数量、费用和交付时间。

购买和付款在双方确认的渠道完成；目前不指定渠道，也不自动发送清单给外部商家。

建议先与少量合作花店、有限服务区域试点，重点验证多品种少支数是否可履约。

技术范围：采购需求单、处理状态、合作商家资料、确认后的供货方案。运营者可先在后台维护资料，商家无需拥有完整的自助入驻页面。

此方式验证供货和购买流程，仍有人工沟通成本。

### 方式 C：FlowerStudio 内统一下单

用户在平台确认方案、下单和付款，由合作商家备货及履约。

需要明确：

- 哪家商家接受该方案、实际价格及可交付时间。
- 缺货、替代与数量变化的确认方式。
- 支付、取消、退款、配送及售后的处理安排。
- 多商家采购是否产生分单、多次配送和不同费用。

商家业务合作和受控资料维护是必要的；开放注册、自助审核、独立商家工作台和复杂结算系统可分阶段建设。

正式交易功能应在合作与履约方式确定后细化。

## 5. 美团接入核实

查阅时间：2026-10-12。

官方页面说明美团生态开放平台提供 API 集成、H5 嵌入及混合模式，合作流程包括申请合作、商务对接、确认方案、开发测试及上线运营。

官方技术服务合作中心的门店管理说明包含门店授权绑定、商品编码配置及订单查询。

这些信息只能证明存在合作与授权渠道，尚不能证明 FlowerStudio 可以获得所需能力，也不能证明它们覆盖鲜花类目的多品种花材购物车或用户侧建单。

需要后续向实际合作方确认的内容：

- 可接入的类目、交易场景与申请主体要求。
- 能否仅跳转店铺或商品，以及可使用的分享链接。
- 是否开放多商品、数量传递或购物车相关能力。
- 商品、价格、库存和订单回传的权限范围。
- 花店是否能按设计配方提供原始花材、小量分拣与配送。

官方来源：

- [美团生态开放平台](https://openapi.meituan.com/)。
- [美团生态开放平台业务指南](https://openapi.meituan.com/guide)。
- [美团技术服务合作中心：门店与订单管理](https://developer.waimai.meituan.com/home/guide/8)。

本次未提交任何合作申请、授权、订单或外部消息。

## 6. 对 UI 的影响

现有首页、工作台、图鉴和作品页保留总体结构。

采购能力开放后，清单页增加“查看可购买方案”入口，并逐步展示：

- 服务区域与所需交付时间。
- 能供货的商家及覆盖的花材。
- 设计用量与需要购买的份数、支数。
- 缺货项与可选替代。
- 经确认的报价、费用和交付方式。
- 对应渠道的动作：前往商家、提交采购需求，或站内下单。

未验证报价和供货前，不将季节信息显示为实时库存，也不以估计值表达最终应付金额。

采购方式可以变化，用户始终从设计清单进入购买方案，避免入口随着渠道变化反复重建。

## 7. 后续业务模块建议

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| M10 商家与供货 | 商家资料、服务范围、供货商品、售卖单位与确认信息 | 引用花材库，保持独立商品标识 |
| M11 采购方案 | 将设计需求映射到供货商品，形成数量、替代与报价方案 | 使用设计配方和供货信息 |
| M12 购买渠道 | 表达人工确认、商家跳转或站内购买的可用方式及状态 | 使用确认后的采购方案 |
| M13 订单与履约 | 站内订单、支付结果、取消退款和配送状态 | 仅在站内交易路线确定后实现 |

上述为最终形态的边界建议，首版不需要实现全部模块，也不需要分别独立部署。

作品、清单、采购方案和订单分别保存对应快照。用户编辑作品、商家更新商品，不应悄悄改变已经确认的报价或订单。

## 8. 推荐的验证与上线顺序

1. 保持写实样片与第一版设计清单的开发目标。
2. 商家合作可行性研究可与产品开发并行，先明确是否支持原始花材按需采购。
3. 在采购试点中采用可核验的商家链接或人工确认需求单。
4. 根据真实购买和履约反馈确定外部渠道或站内交易。
5. 再建设自动报价、库存对接、站内交易或商家自助入驻中确有需要的能力。

图片识别作为已确认的第二批功能，与采购试点的相对上线顺序尚未调整，需后续确定。

## 9. 当前决策

- 当前总体布局作为后续 UI 细化基线。
- 写实视觉与设计到购买的流程作为最终产品方向。
- 第一版范围保持设计、清单、本机保存及登录后跨设备保存。
- 交易路线待定；不因美团等平台存在公开网页而默认获得商品或下单接口。
- 建议先验证少量商家合作，并保留采购渠道可替换的边界。
