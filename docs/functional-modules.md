# FlowerStudio功能模块讨论稿

状态：讨论稿，模块拆分为建议，待与用户逐项确认。

更新日期：2026-10-12

项目依据：工作区中的项目介绍 PDF，以及本次需求讨论。产品正式名称为 FlowerStudio，原 PDF 标题仅为早期昵称。

## 1. 文档用途与推进顺序

本文记录产品功能及模块边界，作为后续工程设计的依据。根据最新讨论，先确认大致 UI，再从页面反推模块与批次。讨论期间持续更新；确认后形成第一版功能基线。

关联文档：[UI 方向与分批实现讨论稿](ui-plan.md)。

最终产品方向：[商家与购买流程讨论稿](purchase-journey.md)。设计需要连接可供货商家与购买流程，具体采用商家跳转或站内交易尚未确定。

产品差异与重复价值：[差异化与用户留存讨论稿](differentiation-retention.md)。个人花器、模板实操指导和成果记录等均为待验证候选，不自动加入首版范围。

工程推进入口：[工程结构与实施路线](implementation-plan.md)。其中 S0、S1、S2 为最新的推荐增量划分，具体技术与细节尚待实施验证。

推进顺序：

1. 确认大致 UI、页面结构与主要交互，再确定功能模块、第一版范围和待定问题。
2. 为各模块补充用户流程、输入输出、状态、异常情况和验收标准。
3. 根据模块关系确定数据模型、前后端职责和接口约定。
4. 确定工程目录、依赖方向、技术选型与开发顺序。
5. 按模块实现与验证，记录后续需求变更。

## 2. 已确认的产品决策

- 目标用户：希望在家 DIY 插花、需要搭配与采购帮助的消费者。
- 第一版目标：完成花束设计并生成花材采购清单，验证设计体验。
- 编辑器同时支持自动排布与手动拖动。
- 两种编辑方式作用于同一份设计，可以切换、组合使用。
- 图片识别放到第二批，首批先完成模板、编辑器和清单。
- 用户可以免登录试用并在本机保存；登录后支持跨设备保存。
- 支持家庭花瓶插花与手持花束，UI 草案先以花瓶插花展示。
- 正式产品名称为 FlowerStudio。
- 花材采用写实方向，插花视觉是重点投入方向；具体采用照片切图、预渲染还是实时 3D 尚未确认。
- 先对比固定视角写实与可旋转 3D 的样片，再决定技术路线。
- 用户认可当前总体布局；默认入口与局部操作仍可细化。
- 最终形态支持从设计与花材清单连接商家并购买，交易路线尚未确定。
- 先讨论功能模块，形成 Markdown 文档，再细化各模块实现。
- 工程设计需要支持后续修改和增强，保持明确的职责与依赖边界。

## 3. 第一版产品流程（建议）

选择模板 / 从零创作
→ 得到初始花材配方
→ 进入同一个编辑器
→ 调整花材、支数和布局
→ 保存设计 / 生成采购清单
→ 复制或导出清单。

说明：首批开放模板与从零创作入口；上传参考图及图片识别在第二批加入。

## 4. 核心业务概念

| 概念 | 含义 | 与其他概念的关系 |
| --- | --- | --- |
| 花材 | 可选择的花种、颜色及必要规格，附带展示素材和基础说明 | 被模板、设计、识别结果和清单引用 |
| 配方 | 某份设计采用哪些花材、各需多少支 | 决定采购内容 |
| 布局 | 花材在画布中的位置、旋转、大小、前后层次 | 决定预览效果 |
| 模板 | 平台发布的初始配方和布局 | 用户从模板创建独立设计 |
| 设计 | 用户当前的配方、布局及作品信息 | 由不同入口创建，供保存与清单生成使用 |
| 识别初稿 | 从参考图推测出的花材及数量 | 用户确认和修正后转为普通设计 |
| 采购清单 | 某一设计版本的花材数量汇总及购买说明 | 保存生成时的快照 |

数量统一以采购单位为准。多头花的花头数量不直接等于支数，素材与采购单位之间的对应规则需要在实现前明确。

## 5. 建议的功能模块

### M01 花材库

目的：建立可用于设计和采购表达的统一花材资料。

第一版候选功能：

- 浏览、搜索花材，按类别和颜色筛选。
- 查看名称、颜色、图片、采购单位及基础说明。
- 从花材库向设计添加花材，或替换现有花材。
- 维护季节参考信息；不将季节信息表达为实时库存。

职责边界：

- 本模块拥有花材资料及素材规则。
- 向其他模块提供稳定的花材标识和资料。
- 不负责用户作品、画布排布、供应商库存或成交价格。

首批内容规模建议：20—30 种常见花材，实际数量按素材准备情况确定。

写实资产与场景能力的职责调整：花材库维护业务资料与采购单位；模型、视角、技术素材及渲染规范建议交由 M09 管理，模块边界待确认。

### M02 灵感与模板

目的：帮助用户快速获得可修改的起始方案。

第一版候选功能：

- 模板列表、封面、简介及风格标签。
- 展示花材组成，选择模板进入编辑器。
- 维护模板的配方和默认布局。

职责边界：

- 模板引用花材库中的花材。
- 从模板创建用户设计时复制初始方案；用户修改不影响原模板。
- 平台后续修改模板不自动覆盖已创建的用户设计。
- 首页可展示模板内容；首页是页面入口，不必单独建立业务模块。

首批内容规模建议：10 套模板。

### M03 花束设计与编辑

目的：让用户调整配方和视觉效果，是产品的核心模块。

已确认能力：自动排布与手动拖动同时支持。

第一版候选功能：

- 从模板或空白画布创建设计；第二批增加识别初稿入口。
- 添加、删除、替换花材，增减支数。
- 根据当前配方自动生成布局。
- 手动拖动、旋转、调整大小和前后层次。
- 撤销、重做、查看预览。
- 将当前设计交给作品管理或清单模块。

职责边界：

- 本模块拥有当前设计的编辑规则和状态。
- 自动排布只改变布局，不能悄悄改变花材配方。
- 手动调整位置、旋转或大小不改变采购支数。
- 增减、删除或替换花材需要同步更新配方与对应的画布对象。
- 三个创建入口共用同一个编辑器，不各自维护一套编辑逻辑。
- 自动排布应可以独立增强，而无需重写保存和清单功能。

待定：重新自动排布如何处理已手动调整的位置，是否提供锁定；画布素材代表一支花还是一组花。

### M04 参考图识别

目的：将参考照片转成可人工修正的花材配方初稿。

第二批候选功能：

- 上传参考图片，展示处理进度和失败状态。
- 识别花材名称、颜色及估计支数。
- 将识别内容匹配到花材库；对不确定或未匹配内容明确提示。
- 用户增删、替换、修正数量后，进入通用编辑器。
- 识别失败时支持重试或直接手动搭配。

职责边界：

- 本模块输出结构化初稿，由用户确认后形成普通设计。
- 编辑器、作品保存与清单生成不依赖某个特定 AI 服务。
- 初期建议使用平台素材构建预览；逐支抠图和精确还原照片布局暂列后续能力。
- 识别结果属于估计，不能直接作为已经确认的采购清单。

已确认：第二批加入。待定：识别范围及可接受的等待时间。

### M05 采购清单

目的：将用户确认的配方转成能用于实际采购的信息。

第一版候选功能：

- 按花材、颜色及必要规格汇总数量。
- 展示名称、小图、支数和购买备注。
- 支持复制或下载清单，具体导出格式待定。
- 用户回到编辑器修改后，可以重新生成清单。

职责边界：

- 清单以确认后的配方为依据，不从预览截图反推数量。
- 清单保存生成时的设计快照；后续编辑不悄悄修改已有清单。
- 若以后允许修改实际采购数量，应区分设计用量与采购用量。
- 价格估算、商家匹配和交易作为后续扩展，不能成为首版清单生成的前置条件。

### M06 作品管理

目的：让用户保留设计并继续使用。

第一版候选功能：

- 保存草稿，恢复上次编辑。
- 展示作品名称、缩略图和更新时间。
- 重新编辑、复制、删除作品。
- 关联作品生成的采购清单。

职责边界：

- 本模块负责设计的保存、读取和归属。
- 编辑器负责编辑行为，不直接承担账号管理。
- 初期只需区分当前作品与清单快照，不默认开发完整的历史版本管理界面。
- 已确认：免登录试用与本机保存，登录后支持跨设备保存。
- 待定：登录时是否主动询问导入本机草稿；本机和云端出现同一作品的不同修改时如何处理。

### M07 内容运营

目的：让运营者持续维护花材和模板。

第一版候选功能：

- 新增、修改花材资料，管理素材和发布状态。
- 创建、修改模板，预览并发布或下架。
- 查看素材缺失、模板引用失效等内容问题。

职责边界：

- 管理页面通过花材库和模板模块的规则修改内容，不维护另一套花材资料。
- 管理页面是受权限控制的入口，不意味着需要独立服务。
- 下架内容不应造成已有作品无法查看；具体保留与编辑规则在模块细化时确定。

### M08 反馈与体验分析

目的：验证用户能否完成设计，并发现体验问题。

第一版候选功能：

- 收集用户反馈及相关作品信息，作品关联需有明确的用户操作。
- 记录进入编辑器、完成设计、生成清单、复制或导出等关键行为。
- 观察各入口的使用情况；第二批增加识别成功与失败情况记录。

职责边界：

- 指标需要明确事件含义，例如“完成设计”采用用户主动确认动作。
- 核心设计流程不应因分析记录失败而无法使用。
- 第一版不默认建设复杂报表系统，先保证数据可用于验证。

### 新增模块建议：M09 视觉资产与场景呈现

写实视觉作为重点方向，建议独立定义该模块，具体边界尚待样片验证。

- 管理照片素材、多角度预渲染或 3D 模型及其版本，与花材稳定关联。
- 负责资产加载、场景呈现、视角及选中对象的识别。
- 内部分清素材生产、资产发布与网页渲染的职责。
- 配方、编辑命令、作品归属和清单汇总继续由各自业务模块管理。
- 具体采用哪些素材和渲染实现，在对比样片后确认。

详见 [写实视觉路线讨论稿](visual-strategy.md)。

## 6. 公共支撑能力

这些能力支撑业务模块，不作为独立用户功能重复建设：

| 能力 | 用途 | 第一版范围 |
| --- | --- | --- |
| 身份与权限 | 区分访客、用户、运营者，保护私人作品和管理入口 | 免登录试用；登录后云端保存；运营权限 |
| 文件与素材管理 | 存储花材素材、上传图片、作品缩略图与导出文件 | 按已选功能配置 |

| 配置与运行记录 | 管理服务配置，记录故障，帮助定位问题 | 基础能力 |

## 7. 模块关系与架构约束（建议）

主要业务关系：

- 花材库 → 模板、编辑器、识别匹配、采购清单。
- 模板 / 经确认的识别初稿 / 空白方案 → 编辑器。
- 编辑器 → 当前设计 → 作品管理与采购清单。
- 内容运营 → 花材库、模板。
- 反馈分析观察关键流程，不控制关键流程。

上述箭头表示业务数据流，具体代码依赖方向将在工程设计阶段确定。

建议约束：

1. 同一份配方和布局数据被自动排布、手动编辑、保存及清单功能共同使用。
2. 花材、模板、作品等有稳定标识，避免靠显示名称关联。
3. 花材计量、设计数量与清单汇总规则有明确归属，避免前后端各自维护不同规则。
4. AI 服务、保存方式和后续采购渠道可以替换，核心编辑规则不绑定外部服务细节。
5. 模块边界先体现在职责、数据和接口上，初期不要求每个模块独立部署。
6. 保存设计的数据格式应考虑版本标识，使后续素材或编辑能力变化时可兼容旧作品。

## 8. 首版范围建议

最终形态包含商家供货、采购方案、购买渠道，以及采用站内交易时的订单履约。建议的 M10—M13 边界详见 [商家与购买流程](purchase-journey.md)。最终目标不改变已确认的首版范围。

首批主流程：花材库、模板、双模式编辑器、采购清单。

支撑功能：本机作品保存、用户登录与云端作品保存、花材与模板运营、基础反馈记录。

第二批：参考图上传与图片识别。

待确认：本机草稿与账号作品的衔接方式；采购清单的导出格式。

暂缓：在线支付、订单、商家入驻、实时库存、物流、多商家采购、社区、会员、完整版本历史界面。

视觉范围更新：写实花材是明确目标，不再把写实呈现整体列为后期功能。实时 3D 的首版范围需通过视觉样片与设备性能验证确定，详见 [写实视觉路线讨论稿](visual-strategy.md)。

暂缓功能未来可通过设计、清单及花材标识接入，不预先实现完整系统。

## 9. 下一轮需确认的问题

1. 是否认可现有功能模块与新增 M09 建议的边界，是否需要合并、增删。
2. 本机草稿在登录时如何导入账号；本机与云端的修改冲突如何处理。
3. 用户账号采用什么登录方式，在模块范围确认后细化。
4. 自动排布与手动调整的切换规则，是否需要锁定已调整对象。
5. 两种设计场景的模板、布局和场景切换规则如何区分。
6. 手机和桌面端的优先级，以及首版必须支持的编辑操作。
7. 采购清单导出格式，是否加入参考价格。

确认顺序：先确认 UI 方向、页面结构与主要交互，再反推模块范围、批次及编辑器数据规则。
