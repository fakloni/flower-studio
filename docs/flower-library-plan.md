# 花材库载入、资料与文件存储评估

评估日期：2026-10-13。

本页保留实施前的评估结论。后续已完成本地结构化导入和网页图鉴接入，当前维护方式见[本地花材库维护指南](local-catalog-guide.md)。

首版方向已确认：先做通用图鉴，暂不绑定地区。现阶段展示有来源的季节参考和搭配资料；地区供货、商家库存及价格留待采购阶段接入。

## 1. 结论

花材库应由花材资料、图片与编辑素材、来源证据组成。文字资料适合结构化存储，图片和模型适合独立文件存储，两者用稳定 ID 关联。

短期可以在本机完成 Excel 清洗和资料录入，生成网站可读取的 JSON，再使用现有静态文件目录展示已核对素材。正式内容管理阶段采用 PostgreSQL 保存资料、对象存储保存文件。云服务厂商要随部署区域确定，当前无需先购买服务。

图鉴图片可以逐步收集；完整、统一角度的单支透明图和准确品种的 3D 模型需要单独制作或筛选。不能把“有照片”直接等同于“可在工作台逐支编辑”。

## 2. 已核实的现状

### 网站

| 内容 | 当前所在位置 | 实际行为 |
| --- | --- | --- |

| 图片样本 | `flower-pic-samples` | 18 张 JPG，经总览检查均为带花器的组合插花图；适合灵感参考，不能直接作为完整单支素材 |
| 用户作品 | `src/infrastructure/local/works.ts` | 浏览器 IndexedDB 的 `flowerstudio-local / works`，保存设计、更新时间和花材 ID；不保存完整花材资料或模型 |
| Excel | 项目根目录 | 尚未被网站读取，也没有导入后台 |
| 云数据库、云端文件库 | 尚未接入 | 依赖中没有现成数据库连接，现有工程文档仅提出方案 |

公开素材目录共有 85 个文件，约 174.47 MiB，其中 `public/assets/flowers` 约 143.02 MiB。目录体积包含未被当前目录引用的候选，不等于页面每次加载体积；当前 3D 代码按作品里使用的模型加载，同一画布实例按 URL 复用加载结果。

现有 `.gitignore` 排除了 `.blend` 原文件、部分原始模型以及 `public/assets/flowers/*.glb` 等。仅依赖代码仓库不足以备份完整资产，需要另存原始文件和清单。此次没有删除或移动这些文件。

### Excel

来源：`花材数据库_产品细分与名称匹配v3.xlsx`，本次只读取，没有修改。

| 工作表 | 内容与实际数量 |
| --- | --- |
| 花材库 | 104 条细分产品或候选，30 列；104 个非空且唯一的产品 ID；关联 57 个不同的非空花材 ID，20 条花材 ID 为空 |
| 名称映射 | 135 条；区分商品类别、同义名、品种、上下位、候选等关系 |
| 尺寸证据 | 70 条；带测量对象、适用范围和来源 |
| 商品规格模板 | 原 57 项花材待采集行；商家 SKU 和已核实供货月份均未填写；同一页另含花器模板和商城映射模板 |
| 图片核对 | 76 条标签记录，均填写对应产品 ID；引用四张旧文件名的图片 |
| 使用说明 | 记录资料口径和使用限制 |

花材库所有行均有角色和形态字段，但其中 17 条角色为“待核定”，另有若干条件性描述，因此不能视为全部角色已经审核。52 条有核实花季／果季，52 条为空；已有季节资料大多是植物志、地区花期或品种花期，并非本地市场供货记录。

工作簿没有嵌入图片，也没有专用图片 URL 列。“图片核对”引用的四个同名文件，在本项目的 `flower-pic-samples`、`asset-sources`、`artifacts`、`public` 中均未找到。现有 18 张样本的文件名和内容无法直接填补这四张文件的对应关系。

“使用说明”C11 仍写 103 条品类，而主表实际有 104 条、B4 的说明也写 104 条；C21 的说明还保留已合并前的“产品品类”表名。导入以实际工作表、列名和产品 ID 为准，并在后续维护 Excel 时更新说明。

## 3. 首版需要录入哪些资料

角色标签应支持多选和适用条件，区分编辑建议与植物事实。例如单头和多头商品、花头大小、枝条形态、作品规模都会影响角色；不把某一种花永久限定为“只能主花”或“不能主花”。

| 资料组 | 建议字段 | 首版处理 |
| --- | --- | --- |
| 身份与分类 | 稳定产品 ID、规范名称、别名关系、大类、小类、物种／品种、核名状态 | 先承接现有 P001–P104；未知身份保留候选，不按名称强行合并 |
| 搭配作用 | 主花、配花、填充、线条、体量、叶材、枝材、果材等多选标签，默认作用、适用条件 | 将现有文本整理成受控标签，人工复核条件和“待核定” |
| 外观 | 颜色／色系、花型、质感、单头／多头、开放阶段、天然／染色／干燥 | 用于图鉴筛选和替代推荐；颜色及处理通常属于具体展示版本 |
| 尺寸与数量 | 枝长、花头测量对象、宽高或直径范围、单位、每枝花头数、销售单位、实测状态 | 保留适用范围；植物高度不当作切枝长，大类参考不当作商品实测 |
| 季节参考 | 花期／果期／栽培期／市场供应等口径，月份区间、来源地区、对象、证据、复核日期 | 首版展示“某地区自然花期参考”；不推导当前库存 |
| 使用与养护 | 修剪要点、支撑需求、瓶插寿命及实验条件、适用场景 | 有资料再填，未知保留空值，不编造统一寿命 |
| 素材 | 素材 ID、用途、对应展示版本、文件位置、作者／来源、授权记录、审核状态、版本 | 每份素材单独记录，不能一个图片字段兼任所有用途 |

录入时需要先确定字段体系，但不需要等所有资料集齐才开始使用。资料状态应按字段区分，允许“已核名、角色待审核、季节未知、图片待补”的记录存在。

建议将展示能力分开：

- 图鉴可浏览：规范名称、身份核对状态、已核对图片或明确的缺图占位、来源说明。
- 可提供搭配建议：角色和主要外观资料已审核；季节未知时不参与季节判断。
- 可加入编辑器：另有通过检查的单支图片或模型，单位和单支数量映射明确。
- 可参与采购：另有商家商品、配送地区和有效的供货记录。

## 4. 季节提示和替代建议

通用图鉴首版不输出“当前季节没有这种花”。可显示“这条资料记录的是某地区的自然花期；市场供应尚未核实”，或者“季节资料待补充”。对于没有地区定义的记录，不设置默认的全国供货月份。

后续加入采购能力时，分开管理三类信息：

1. 自然花期或果期：解释植物季节性。
2. 供应商供货月份：按产地、配送地区、商品和来源维护。
3. 实际库存或可采购状态：记录核查时间和有效期，过期后回到“未确认”。

跨年区间如“9月至翌年3月”必须按 9、10、11、12、1、2、3 月处理；未知月份不是无货。地区、供货日期和商品规格缺失时，不自动判定不可采购。

用户已经拥有的花材应以用户确认的持有情况为准。季节提示用于后续补买和计划采购，不否定用户手头已有的花，也不自动从作品移除。

替代推荐首版可以使用明确规则和人工维护的候选关系，无需先依赖 AI：

- 先保留原花材在作品里的作用，以及用户锁定的颜色、造型或尺寸要求。
- 再比较花型、花头体量、枝长、线条形态、质感及开放阶段。
- 有采购条件时再过滤有效供货、配送范围和预算；没有这些数据时仅给出风格替代候选。
- 展示替代理由和差异；替换多头与单头商品时重新计算枝数，不能默认一支换一支。
- 同义名匹配、同品类候选、风格替代分别标注。不能把小菊当作乒乓菊的同义名。

## 5. 图片收集可行性

| 图片／资产类型 | 可行性判断 | 采集方式 |
| --- | --- | --- |
| 常见花材的大类图鉴照片 | 可以逐步收集 | 自有拍摄、供应商授权图、开放许可图库；先核对花种和对应范围 |
| 精确品种、颜色和开放阶段照片 | 需要定向采集 | 商家或育种方资料、自行拍摄；普通图库图不能代表同款商品 |
| 统一视角、完整单支透明图 | 需要额外制作和验收 | 统一背景拍摄后处理，或由合格模型渲染；整束图有遮挡时无法可靠拆出完整单支 |
| 3D 单支模型 | 工作量高，单独推进 | 筛选现有模型、加工或建模，验证单支、尺寸、背面和网页表现 |
| 组合插花图片 | 已有 18 张参考样本 | 用于灵感和风格研究；不能据图保证每种花的实际支数或供货季节 |

Wikimedia Commons 可作为图鉴候选来源，逐图查看物种标注、作者和许可证。Pexels 可补充花材和插花参考，具体品种及单支完整性仍须核对。图库存在并不代表 104 项精确品类、品种和阶段已经有合适图片，本轮没有批量下载或发布新素材。

先选 10–20 项核名较明确、角色覆盖主花／配花／叶材／线条的常见产品做试点。每项先收集一张可辨认的图鉴图，按需要补花头近景和完整单枝图；优先复核已有工作台 6 项与 Excel 产品的映射，未匹配项单列，不强行绑定。

每张图的最小记录：素材 ID、产品／展示版本 ID、来源页面、作者、原文件、授权依据、取得日期、用途、花型／颜色／阶段、尺寸、审核状态。采集和发布是两个状态；公开文件只放审核后的版本。AI 图如用于概念或补充展示需明确标识，不能作为核名、真实花径或真实品种的证据。

## 6. 文件应该存在哪里

网站不要求所有文件放在同一台机器。这里将“网站程序”“花材资料”“图片和模型”分开管理，具体可以在同一云平台，也可以使用不同服务。

| 内容 | 本机试点 | 正式网站 |
| --- | --- | --- |
| 网页代码 | 项目源码和代码仓库 | 网站部署服务 |
| 花材、别名、角色、季节、尺寸、证据 | 经校验的结构化 JSON；Excel 为录入来源 | PostgreSQL；数据库保存文件引用和业务资料 |
| 原始 Excel 和导入报告 | 原表保留，批次归档 | 私有文件库，用于追溯；访客无需下载原表 |
| 原图、拍摄资料、授权文件、Blender 源文件 | `asset-sources` 及独立备份 | 私有对象存储或资产归档；单独备份 |
| 已发布图鉴图、缩略图、透明图、GLB | `public/assets` 下按用途管理 | 公开对象存储，按访问需要配合 CDN |
| 用户私人上传图片、未公开作品图 | 本机保存或后续上传入口 | 私有对象存储，按用户授权访问 |
| 作品结构 | 保留 IndexedDB 本机草稿 | 有账号时增加数据库云端保存；引用稳定花材与素材版本 |

“对象存储”可以理解为网站专用的文件库。数据库管理花材的名称、标签和文件位置，文件库保存图片及模型本身。一般不把原图或 GLB 当作大段 Base64 写进花材资料表，也不把运行中的网站服务器磁盘当作永久上传盘。

云端厂商候选：国内部署可评估 OSS 或 COS；若部署环境适合 Supabase，可评估其 PostgreSQL 与 Storage 组合。最终依据部署地区、访问效果、运维方式和存储／流量需求选型，当前不锁定厂商或报价。

建议文件路径采用稳定 ID、用途和版本，例如 `catalog/P052/variants/<variant-id>/v1/cover.webp`、`.../cutout-front.webp`、`.../stem.glb`。原文件和发布文件分别记录；相同花材的不同色彩、阶段或模型版本不互相覆盖。数据库保存 bucket 与 object key 等稳定引用，临时访问链接在需要时生成。

图鉴列表只请求缩略图，详情页再取清晰图，加入作品后再取该花材的编辑素材；不会因为有 104 条目录就下载 104 个 GLB。批次备份要同时保存数据库记录、文件和对应版本清单。

## 7. 建议的数据组织与载入流程

逻辑上区分以下内容；本机阶段可以保存在同一份 JSON 中，不要求立即建设全部数据库表：

| 内容 | 标识与关系 |
| --- | --- |
| 花材产品 | 承接 Excel 的 P 产品 ID；F 花材 ID 可为空，不当作产品唯一键 |
| 展示版本 | 对应产品，区分颜色、开放阶段、处理方式及花型 |
| 别名关系 | 对应产品并保留关系类型；一对多、上下位和待核候选不折叠成单一精确匹配 |
| 角色与使用条件 | 绑定产品或展示版本，可多选，保留审核状态 |
| 季节与尺寸证据 | 保留口径、对象、地区、单位、范围、出处和复核日期 |
| 素材 | 对应产品或展示版本，独立用途、文件版本与来源记录 |
| 商家商品与供货 | 后续增加；具体 SKU 对应产品／版本及有效供货记录 |

推荐载入流程：

1. 保存原始 Excel 和文件校验值，建立导入批次。
2. 分别解析花材库、名称映射、尺寸证据、图片核对，按列名读取。商品规格模板内有多个分区，不能整页视为同一种记录。
3. 以产品 ID 校验唯一性，检查别名目标和素材关联。20 个缺失 F ID 的候选保留其 P ID 与待核状态。
4. 将角色文本整理为标签和备注，将月份整理为区间；保留原文，无法明确解析的项进入复核清单。
5. 将空白、范围、严格小于、上限、通常值和实测值区别保存。尺寸证据只绑定到适用对象，不无条件分发到同一 F ID 的全部产品。
6. 建立图片文件清单，补回四张旧文件的来源映射；名称相近不能代替人工确认图片内容。
7. 输出“新增／更新／待复核／缺图”的预览，审核后发布通用图鉴数据快照。
8. 网站列表读取轻量目录，详情按需读取证据与大图，工作台仅开放具有合格编辑素材的记录。

重复导入按稳定产品 ID 更新，不能按行号生成新 ID。人工维护的新资料不能被旧表中的空白覆盖；冲突保留供复核。现有作品使用 `pink-rose` 等 ID，接入新目录时需保留兼容映射及素材版本，避免旧草稿失效。

## 8. 下一阶段的具体范围

先做本机通用图鉴试点：确定字段与审核状态、清洗 104 条记录、为 10–20 项补齐图鉴图和角色资料、验证导入与按需载入。试点通过后再接内容管理后台、PostgreSQL 与对象存储。当前不依赖地区供货数据，不发布“当季无货”的判断。

本次交付是现状评估与方案；没有修改网站行为、Excel 或现有素材，也没有创建云端服务。
