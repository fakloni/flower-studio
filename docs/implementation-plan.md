# FlowerStudio：工程结构与实施路线

状态：实施中。已按照用户认可的工作台概念稿完成可交互本机原型；后续里程碑仍按本计划推进。

更新日期：2026-10-13

当前项目已有 Next.js / React / TypeScript 工作台代码、六种花材与两款花瓶的可交互网页预览，详见[运行说明](../README.md)。素材来源与编辑文件仍见[素材库](../artifacts/asset-library/README.md)。

S0 已有[工作台设计基线](workbench-design-spec.md)、[桌面 / 手机设计稿](../artifacts/workbench-design/README.md)和[精简样片素材包](workbench-sample-pack.md)。网页默认使用 Three.js 的 3D 路线，保留图片预览用于比较与加载失败时切换；正式渲染路线仍需精修素材并经过真实设备评估。

S1 已实现模板、按支编辑、手动拖动/旋转、换瓶、撤销/重做、清单快照、IndexedDB 自动保存与恢复、作品文件导入导出；S2 已提前实现手机底部面板和本机作品管理。账号、云端保存、运营后台与采购仍待实施。当前样式采用共享设计变量与组件类，尚未拆成 CSS Modules。

## 1. 建设目标

先形成可实际体验的产品，再逐步增强内容、账号和采购能力。

最小完整流程：我的花瓶 / 选定场景 → 选择模板或从零开始 → 写实预览与编辑 → 生成花材清单 → 保存 → 重新打开继续编辑。

长期流程：设计清单 → 匹配可供货商家 → 确认购买数量、替代与报价 → 通过可用渠道采购。

原有第一版目标保持不变：设计、清单、免登录本机保存，以及登录后跨设备保存。图片识别在第二批接入。

“我的花瓶”与可实现模板作为优先验证方向：先以常见花器、基础尺寸和少量经实物验证的模板开始。个性化推荐、任意设计自动生成教程、持有花材管理仍需另行确认。

## 2. 总体架构建议

采用一个代码仓库、一个 Web 应用，内部按业务模块组织。页面与后台接口可部署在同一应用中。

职责分为四部分：

1. 页面与操作：导航、编辑器控件、图鉴、作品页和采购页。
2. 业务规则：花材实例、配方、编辑命令、布局与清单汇总。
3. 渲染：素材加载、画面呈现、视角、对象拾取与图像导出。
4. 外部能力：本机存储、数据库、文件、账号、后续 AI 和采购渠道。

页面调用模块提供的能力；业务规则保持独立；渲染与存储通过明确接口接入。

目录按实际开发范围逐步创建，不为所有远期模块提前生成空工程。

## 3. 推荐技术组合

| 部分 | 建议 | 原因与采用阶段 |
| --- | --- | --- |
| 页面与后台入口 | Next.js + React + TypeScript | 在一个工程中组织公开页面、浏览器工作台及后台接口 |
| UI 样式 | CSS Modules 与统一设计变量 | 先落实已认可的布局、间距、颜色和控件样式 |
| 编辑规则 | 独立 TypeScript 模型、命令与状态归约 | 可单独验证数量、撤销、保存等规则，保持对渲染库独立 |
| 本机保存 | IndexedDB，按需要使用 Dexie 封装 | 支持结构化作品及缩略图等数据，先交付免登录流程 |
| 3D 候选 | Three.js + glTF / GLB | 用于可旋转的真实模型样片；正式采用待验证 |
| 固定视角候选 | 图片素材与轻量 2D 场景实现 | 用真实切图或预渲染素材完成对照；具体工具在样片阶段选择 |
| 资产制作 | Blender 与经确认的拍摄 / 模型来源 | 制作或处理模型、纹理、多角度图片，独立于网页运行 |
| 云端数据 | PostgreSQL | 第一版完善阶段加入账号归属、发布内容及设计文档保存 |
| 文件 | 对象存储，独立文件引用 | 存放发布素材、缩略图与用户文件；服务提供方按部署环境选定 |
| 账号 | 选定成熟认证方案 | 登录方式确定后接入，统一由后台验证用户身份与作品权限 |

这里的技术组合是项目建议，不代表已经安装、实现或锁定全部依赖。

工程初始化时确认版本、锁定依赖和运行环境；数据库工具、认证提供方与部署服务随具体阶段选定。

初期编辑状态可以先由 React useReducer 连接独立规则；如果实际交互需要更细的订阅粒度，再评估专用状态工具。

官方能力依据：

- [Next.js Server / Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)：区分服务端页面数据与浏览器交互。
- [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)：组织 HTTP 接口入口。
- [React useReducer](https://react.dev/reference/react/useReducer)：根据动作与规则更新状态。
- [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)、[Dexie](https://dexie.org/docs)：本机结构化数据存储及其封装。
- [Three.js GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)：glTF 模型加载候选。
- [PostgreSQL JSON 数据](https://www.postgresql.org/docs/current/datatype-json.html)：可用于设计文档内容；关联数据仍应有明确约束。

```text
├─ src/
│  ├─ app/                       页面、导航、后台 HTTP 入口
│  ├─ modules/
│  │  ├─ catalog/                花材业务资料
│  │  ├─ templates/              配方、布局和模板内容
│  │  ├─ design/                 设计文档、编辑命令与操作界面
│  │  ├─ vessels/                花器定义、尺寸与用户选择
│  │  ├─ works/                  草稿、作品及保存流程
│  │  ├─ shopping-list/          花材清单汇总与导出
│  │  └─ visuals/                渲染约定、素材加载与实现
│  ├─ infrastructure/
│  │  ├─ local/                  本机存储实现
│  │  └─ server/                 数据库、文件和认证连接
│  └─ components/ui/             通用按钮、面板、表单等
├─ public/assets/                少量发布用测试素材
├─ content/                      早期花材、花器和模板数据
├─ asset-sources/                原始素材说明及可管理源文件
└─ tests/                        关键规则与主要流程验证
```

模块内部根据实际需要使用 `model/`、`commands/`、`ui/`、`server/` 等子目录。规模很小时可保持少量文件，职责清晰后再扩展。

页面目录主要负责组装模块。花材数量、清单汇总和保存规则放在对应模块内。

本机存储与云端存储实现同一套必要的保存约定。云端新增权限和冲突检查，不能简单把本机操作当作已授权的云端操作。

服务端连接使用独立入口，浏览器模块不能导入数据库或认证密钥。模块不同时通过一个总入口导出客户端和服务端实现。

商家、采购方案、订单和 AI 目录在各自进入开发阶段时再添加。

大体积 Blender 源文件与模型按实际情况使用独立资产存储或大文件管理；发布素材有来源、版本及对应标识。正式资产与用户私人上传文件使用各自访问规则。

## 5. 最先确定的数据关系

### 5.1 一支花与一个视觉对象

一支实际花材对应一个逻辑花材实例，具有稳定实例标识。多头花在画面里可以包含多个花头，但采购数量仍按实际支数计算。

建议以逻辑花材实例作为设计数量的权威来源：

- 用户增加一支 → 创建一个实例。
- 删除一支 → 删除相应实例。
- 拖动、旋转 → 修改实例的摆放信息。
- 清单 → 从实例汇总需求数量。

画布节点、花头网格数量或缩略图不能作为采购数量来源。若将来支持一组花材作为一个对象，需要增加明确的数量映射规则。

### 5.2 设计文档

设计文档至少包含：

- 作品标识、名称、格式版本。
- 花瓶插花 / 手持花束场景。
- 花器引用和尺寸，附明确计量单位。
- 花材实例，引用花材及视觉资产版本。
- 摆放信息，按照样片确定的二维或三维格式保存。
- 与查看有关的可选配置、缩略图引用和保存时间。

二维与三维坐标可用不同结构表达。具体坐标和姿态规则在样片后定稿，不假定任意平面设计可无损转为 3D。

保存稳定、可序列化的设计数据。渲染引擎的相机、网格或材质对象由渲染层重建。

### 5.3 配方与采购

模板创建独立作品；用户修改作品不改变模板。

清单保存生成时的配方快照。后续商家售卖单位、购买数量、价格与订单拥有各自记录，不写入设计花种的固定属性。

### 5.4 内容与素材

花材名称、品种、颜色和采购单位属于花材库。模型、图片、视角、加载资源及技术版本属于视觉资产。

素材变更需有版本约定，旧作品继续引用已发布资源，或执行明确的迁移与提示。

## 6. 实施步骤

### S0：UI 基线、工程基础与写实样片

#### S0-A：先形成可指导实现的 UI 基线

用户已认可总体布局；正式开发前进一步确定以下内容：

- 品牌、整体视觉气质、主色和背景，字体、间距、圆角及控件样式。
- 配置页的花材选择、中央预览、配方与数量、花器场景及保存 / 清单动作。
- 桌面和手机的主要布局，手机面板展开与画布操作的关系。
- 空白、已选中、自动搭配 / 手动摆放、保存中 / 失败等关键状态。
- 写实花材、花器和背景的呈现规范，围绕实物比例而非装饰效果。

交付物：风格板、桌面 / 手机配置页设计稿、核心操作流程及少量组件规范。

通过条件：这些资料足以指导第一张正式页面实现。其他页面在同一规范下逐步展开，写实样片结果仍可用于校准画布与操作细节。

#### S0-B：搭试验工程并验证写实路线

先做的事：

1. 建立版本管理、开发运行方式、格式检查及统一文档入口。
2. 用极简 Next.js + TypeScript 工程承载样片和既有布局方向。
3. 先用一种花材和一个花瓶验证加载与交互，再扩展到玫瑰、康乃馨、尤加利的代表性对比。
4. 统一素材比例、轴向、插入点、计量单位和来源说明。
5. 做固定视角写实与可旋转 3D 两个可运行样片。

有合格 3D 源资产时，可从同一模型输出透明预渲染图片与 GLB，以降低比较中素材质量差异的影响；真实照片作为质感参考。照片切图路线也需用自己的合格样本验证。

样片只需：添加几支、删除、拖动或调整姿态、观察效果，以及记录加载和交互表现。

交付物：两套可运行样片、素材规范初稿、目标设备测量记录和渲染路线决策。

通过条件：可以判断视觉是否可信、用户是否更容易判断搭配、手机是否可用，以及每种新增花材的制作与维护是否可行。明确代表性设备和测量条件后再定性能预算。

此阶段为必要验证。取得高质量模型或照片是实际前置条件；程序生成的简易花朵或一张 AI 效果图不能作为真实 3D 编辑能力的证明。

### S1：跑通免登录完整流程

样片选择路线后：

1. 定稿设计文档格式、编辑命令、清单汇总和存储约定。
2. 实现花瓶插花与手持花束的基础场景。
3. 使用少量花器与 3—5 个有明确配方的模板。
4. 以插花配置页 / 工作台作为第一张完整业务页面，先串联模板进入、清单和草稿恢复，再完善首页及其他页面。
5. 支持增减、替换、自动排布和手动拖动。
6. 支持基本撤销、清单复制与 IndexedDB 保存。

花材和模板先由版本化内容数据提供，数据形状与后续后台一致。

交付物：可以从头使用并保存的本机版。

通过条件：用户能完成设计并获得正确支数清单；刷新后恢复同一份设计；重新排布或切换编辑方式不改变配方；模板原稿保持独立。

### S2：完善第一版

基于 S1 完成：

- 对象旋转、层次等必要操作，完整撤销重做和明确的选中反馈。
- 我的作品、复制删除、清单导出。
- 图鉴、手机展开面板与关键异常状态。
- 少量经实际验证的模板指导，保存选定花器及基础个人条件。
- 登录、账号云端保存、跨设备读取与本机草稿导入。
- 花材与模板运营管理，逐步扩展素材覆盖。
- 基础反馈与体验记录。

后台在这一阶段接入 PostgreSQL、文件存储和认证；可以按内容管理、作品保存分别小步交付。

登录后的保存需能识别修改冲突，优先采用清楚的版本检查与“另存副本 / 选择保留版本”，实时多人协作不属于当前目标。

交付物：符合此前第一版目标、可邀请用户试用的版本。

通过条件：桌面和手机的核心流程可用；另一设备能恢复账号作品；保存失败有可恢复状态；不同账号作品保持各自权限；运营更新不会使旧作品静默变化。

### 后续支线 A：第二批图片识别

增加参考图上传、任务状态、花材匹配、用户修正，最后创建普通设计文档交给既有编辑器。

处理任务放在后台，模型密钥不进入浏览器。长时任务的执行方式与队列在此阶段选择，保留失败、取消或重试状态。

交付物：可确认与修正的识别初稿入口，其他设计入口正常运行。

### 后续支线 B：采购试点与交易扩展

商家合作可行性研究可以与 S1 / S2 并行。采购功能先建立需求单和经核实的供货方案，明确少量多品种花材是否能买齐。

随后依据合作结果选择商家链接、授权渠道或站内交易。具体上线顺序与第二批识图的关系仍待确定。

站内交易方案成立后，再细化订单、付款、配送及售后；商家自助入驻根据运营需要增加。

交付物：可核实的设计到采购流程，实际设计用量与购买数量清楚区分。

## 7. 前后端的执行边界

前端负责：

- 即时编辑、视角、选中状态与交互反馈。
- 本机草稿和恢复流程。
- 呈现来自后台的花材、模板、账号作品及供货信息。

后台负责：

- 身份、权限、内容发布、云端作品与文件引用。
- 校验设计数据格式、花材引用及必要的版本约定。
- 后续识别任务、供货方案和交易状态。

拖动花材可以即时在渲染层预览，完成一次动作后形成编辑命令、撤销记录和保存更新。连续拖动不要求每一帧请求后台或重绘整个 React 页面。

自动保存应合并短时间内的更新，并清楚表达保存状态；离开页面和恢复场景需要专门验证。

## 8. 修改与增强的约束

1. 编辑命令和数量规则不依赖 Three.js、DOM、数据库或 Next.js 路由。
2. 模块通过必要的公开入口协作，避免直接修改另一个模块的内部状态。
3. 渲染层消化统一的设计数据；素材版本和坐标约定明确。
4. 本机与云端保存通过必要接口接入，云端增加身份和并发校验。
5. 清单从配方计算，采购从供货商品计算，订单保存确认后的快照。
6. 公共 UI 复用外观与交互，业务判断保留在业务模块。
7. 主工作台只采用已选择的渲染方案，对照方案保留为实验依据；新增渲染器按实际需求推进。
8. 设计格式和内容版本发生变化时，先定义迁移与兼容行为。

## 9. 验证策略

工程建立后，优先验证真正影响作品和清单正确性的规则：

- 多头花的支数映射。
- 增减、替换、删除和撤销重做。
- 保存 / 恢复，以及格式迁移。
- 清单快照不随后续编辑静默变化。
- 登录导入、云端版本冲突和作品权限。

主要流程做浏览器验证：模板 → 编辑 → 清单 → 保存 → 重新打开，覆盖手机操作和资源加载失败。

每个已完成阶段执行对应检查，新的修改或风险出现时再扩展验证。写实资产还需要视觉检查和目标设备实际测量。

## 10. 本轮建议的下一项工作

启动 S0，按顺序形成：

1. UI 风格基线、桌面 / 手机配置页设计稿和核心操作流程。
2. 最小试验工程。
3. 从一种花材和一个花瓶开始的素材记录，扩展到代表性花材。
4. 两种可运行视觉样片及对比结果。

选定渲染路线之后，进入设计模型和 S1 配置页主流程。UI 基线先提供实现约束；工程基础可与素材准备交错推进；核心编辑数据应在样片结果支持下定稿。
