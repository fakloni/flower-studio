# 花材识别与花束生成：API 可行性及评测方案

核查日期：2026-10-27。本文保留 API 调研、计费口径与完整评测路线。第一版识花脚本和配置已放在同一文件夹，使用方法见 [README](README.md)。尚未调用付费模型、未产生模型实测结果；公开文档支持不等于当前账号已获调用权限。

## 1. 结论与范围

- 技术可行。可以把 5 张花材照片、1 张花瓶照片和 1 张场景照片一起传给支持多图输入的生图模型，再用文字明确每张图的用途。
- 推荐主要输入方式为“照片 + 花名/编号 + 约束文字”。另设纯文字和图片不带花名的对照组，比较实际增益。
- 识花和生图是两个独立评测任务。后续产品可以各选一个模型，但评测阶段应支持多模型，不需要先锁定两个。
- 建议先写一个本地可配置评测工具，先完成识花，再增加生图与人工盲评。当前阶段不需要先开发网页后台。
- 用户列出的 9 个生图候选有对应官方文档。11 个识图候选中，两个指定的 DeepSeek V4 GA 版本没有列入火山方舟视觉理解模型，应先排除，剩下 9 个可作为直接识花候选。
- API 能接收参考图，并不保证花材身份、支数、花器和场景都严格保持；这些必须成为测试项。

### 2.1 实际如何传入 5 种花

推荐分别传入原始图片，不先拼成一张九宫格。保持每张花材的细节和明确顺序：

1. 图 1—5：五种花材，每张配稳定编号和经人工核对的名称。
2. 图 6：花瓶，说明哪些外观必须保留。
3. 图 7：场景，说明是参考风格，还是要求保留原场景。
4. 文字：每种花数量、颜色、开放程度、构图、花束轮廓、允许和禁止的变化。

提示词应表达类似意图：“图 1—5 分别对应花材 A—E，保持各自花型和颜色；仅使用这五种花材；将其插入图 6 的花瓶；使用图 7 的场景与光线。支数和位置按清单执行。”具体模板后续应版本化。

先分别评测两种任务，不能混为同一个约束难度：

- **参考场景生成**：重新生成花瓶和环境，要求外观接近参考。适合设计预览。
- **在原场景中编辑**：以用户原照片为底图，在指定区域加入花束，检查花瓶、桌面、背景是否被改动。有局部编辑能力时可使用遮罩；严格保留背景还可结合确定性图像合成。单靠提示词不能把它当作像素级保证。

图片无法可靠提供真实厘米尺寸。花瓶高度、瓶口直径和花茎长度等如要评测，应额外输入测量值，并区分“视觉比例合理”与“真实几何可实现”。

### 2.2 三组输入对照

| 组别 | 输入 | 要回答的问题 |
| --- | --- | --- |
| A：纯文字 | 花名、数量、花瓶和场景描述 | 模型仅凭名称能做到什么程度 |
| B：参考图 + 编号 | 花材图、花瓶图、场景图及约束，不给花名 | 模型能否理解和保持参考外观 |
| C：参考图 + 已核实花名 | 与 B 相同，再加入花名 | 实际产品推荐工作流，验证名字与图片结合的收益 |

生图独立评测应使用人工核实的花名。另做“识花结果 → 生图”的端到端测试，才能区分识花错误与生图错误。

### 4.3 记录费用时的规则

- 读取服务端原始用量，同时保留原始响应，按厂商、接口、型号和价格版本归一化。
- 区分未缓存输入、缓存读取/写入、图片输入、可见输出、思考用量、图片输出及工具调用。细分字段与总量可能重叠，不能重复相加收费。
- 字段未返回时记 `null/unknown`，不能填 0；按张收费的图片费用在有足够张数和规格时仍可以估算。
- `estimated_cost` 是“服务端用量 × 保存的价格规则”；`billed_cost` 仅在能从供应商账单核对时填写。免费额度和折扣另记，保持模型标价与实际支出可区分。
- 原币种和金额必须保留。汇总成人民币时保存汇率值、来源与日期。
- 每次尝试单独记录。失败、超时和重试可能涉及已经完成的请求；超时后的费用未知，不能一律按免费处理。
- 同时算“每次调用成本”和“每次成功识别 / 每张合格图片成本”。后者把重试和不合格结果消耗计入分子，更接近产品真实成本。

## 5. 当前项目数据能否直接使用

已只读检查现有结构：

- `data/catalog/catalog.json` 有 104 条产品或候选、135 条名称映射、76 条图片参考记录。
- `data/catalog/assets.json` 有 26 个素材条目，其中明确标为 `photo / real-photo` 的 10 个；这 10 个均标为 `category-or-variety-reference`。
- 因而“104 个目录条目”不等于“104 类已经有经核实的测试照片”。原表图片引用、图鉴素材、模型预览图也不是同一种数据。
- 目录包含上位类、花型、商品形式和别名，部分条目并非互斥分类。不能把 104 个 ID 当成无歧义的 104 分类任务。

建议复用已有产品 ID、名称和素材路径，新增单独的评测清单，避免修改生产目录和原 Excel。每个样本应有：样本 ID、图片路径与校验值、可接受标签、可确认层级、大类、小类、品种是否已核实、颜色、单/多头、开放程度、来源、标本/拍摄组、人工复核状态。

识花样本先仅使用真实照片，生成图、3D 渲染图另建专项集。输入使用匿名编号和图片内容，不能把真实花名、含答案的文件名或来源页面一起发给模型；图片里本身的花名标签、包装文字和水印也要检查，避免测成读字。若裁切或遮挡文字，应保存处理规则和原图。

同一标本或同一来源的近似图不要跨调参集与最终测试集。不能用测试图片本身作为检索参考，再把检索命中当成未见图片识别能力。

## 6. 识花如何评

建议分两条测试路线，各自报告：

- **开放识别**：只有照片，输出规范名称、可接受别名、Top-3 候选及“不确定”。用于衡量模型自身识花能力。
- **花材库内匹配**：给经过整理且版本固定的候选目录，输出候选 ID 或 `unknown`。用于衡量产品实际找库能力；目录本身的 token 成本也要计算。

先用固定结构返回结果，字段包括大类、小类、可选品种、Top-3、可见属性和是否无法判断。品种无法从照片确认时允许留空，不强制编造。

| 维度 | 指标 | 口径 |
| --- | --- | --- |
| 正确率 | 大类 Top-1、小类 Top-1、Top-3 | 按每张图可确认的标签层级分别统计；同义名先规范化 |
| 类别均衡 | 各类正确率及宏平均 | 避免大量常见玫瑰掩盖少见花材表现 |
| 不确定性 | 无法判断比例、拒识后的正确率、库外误接收率 | 统计模型是否乱猜；不确定样本不能悄悄从分母删除 |
| 可用性 | 结构化结果有效率、接口成功率 | 把不会返回可解析答案和认错花分别记录 |
| 速度 | 完整可解析结果的 P50 / P95 | 首字速度可附加记录，但主指标应为拿到可用答案的时间 |
| 成本 | 单图平均、每千图、每次正确结果成本 | 覆盖用量、重试和未知费用状态 |
| 稳定性 | 同图重复测试一致率 | 对入围模型及易混类别做重复测试 |

模型自己报的 confidence 不是经过校准的正确概率。第一版可保留但不据此直接做跨模型排名；后续在独立数据上校准阈值。

上位类回答不能自动算细分类答对：例如真实标签为可确认的乒乓菊，仅答“菊花”可以算大类正确、小类未命中。仅能确认“玫瑰”的样本，不应用来判定具体栽培品种正确率。

错误映射和难例需人工复核；评分规则与别名表应固定版本，不能为了某个模型临时放宽。

## 7. 生图如何评

“效果”拆成以下项目，建议采用隐藏模型名、随机排列的人工盲评；如用另一个模型初筛，也要单列其费用并抽样人工校准。

| 指标 | 检查内容 |
| --- | --- |
| 花材忠实度 | 每一种指定花材能否辨认，颜色、花型、花瓣及叶片是否保留 |
| 花材覆盖率 | 五种是否都出现；是否遗漏或擅自新增其他花材 |
| 数量遵循 | 按约定统计支数或可见花头；遮挡不可判断要单列，不能当成精确计数 |
| 花瓶遵循 | 形状、瓶口、材质、颜色、纹理是否保持；花束与花器比例是否合理 |
| 场景遵循 | 背景、光线、摆放区域和透视是否符合要求 |
| 视觉合理性 | 花茎连接、重叠遮挡、穿模、悬浮、玻璃折射等是否合理 |
| 花艺与美感 | 配色、疏密、层次、主次和整体完成度，可用 1—5 分 |
| 稳定性 | 同一任务生成 3 次的合格率和波动 |
| 速度与可靠性 | 最终图片可获取的 P50/P95、下载完成时间、失败率、重试次数 |
| 成本 | 每次尝试、每张完成图、每张达到合格标准的图片成本 |

建议先设硬性合格标准：指定花材齐全、无额外花材、花瓶/场景关键约束通过。再比较合格图的美感。不能让很漂亮但换掉花材的结果靠平均总分胜出。

尺寸不完全兼容：Seedream Lite 最低 2K，而 Gemini Flash Lite Image 仅 1K。不存在所有 9 个候选都能遵循的统一 1K/2K 档位。应分别建立 1K 与 2K 比较组，不支持的配置记“不支持”，或在实际产品档位测试中明确记录原生输出尺寸与费用；缩小后展示的图片仍按原始生成尺寸计费。其他模型也要验证确切像素限制，不能只比较“2K”这个名字。[Seedream 尺寸约束](https://docs.volcengine.com/docs/ark/image-generation-api?lang=zh)、[Gemini Lite 输出尺寸](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite-image)

## 8. 脚本应如何设计

第一版已使用 Node.js 原生模块实现独立命令行工具，无需新增依赖。它不依赖页面组件，后续网页可以读取报告和结果文件。当前布局如下；本节后续的并发、重试、断点续跑和严格金额预算等属于完整路线，不能理解成第一版全部已实现，功能边界见 README：

```text
evaluation/
  README.md
  api-analysis.md
  config/models.example.json # 模型、协议、参数、原币种价格与生效期
  datasets/                  # 标准答案格式、自动生成的待核清单
  prompts/                   # 识花提示词、生图用例设计
  src/cli.mjs                # 本地预检、识花调用、离线重新评分
  src/core.mjs               # 评分、用量与费用、结果汇总
  src/providers.mjs          # 三家原生协议
  tests/                     # 离线测试，不调用付费 API
  runs/<run-id>/             # 本地结果，不提交 GitHub
```

不是只填一个 API key 就能自动兼容所有平台。配置至少需要：

| 类别 | 配置内容 |
| --- | --- |
| 连接 | 渠道、base URL、原生协议、key 对应环境变量名、区域 |
| 模型 | 完整 model ID、固定版本、任务、图片输入能力和上限 |
| 参数 | 图片预处理、输出尺寸/质量、思考强度、输出上限；不支持的参数不发送 |
| 调度 | 单模型并发、限流、超时、重试上限、预算上限 |
| 计费 | 原币种、价格规则 ID、生效时间、渠道折扣（如有） |

key 只放本地环境变量或已忽略的本地配置中；提交的示例只写环境变量名称。日志应去掉授权头，不保存密钥；已有花材名和文件路径也要与发送给模型的匿名输入分开。

每次请求至少保存这些结果：

| 分类 | 字段 |
| --- | --- |
| 复现 | run/sample/task ID、模型开发方、服务渠道、请求/返回 model ID、接口与请求 ID、时间、提示词/数据集/参数版本、图片校验值 |
| 执行 | attempt ID、状态、错误码、重试次数、开始时间、请求耗时、完整结果耗时、下载耗时 |
| 用量 | 原始 usage、归一化输入/输出及可得明细、输入/输出图片张数、实际尺寸 |
| 费用 | estimated_cost、可选 billed_cost、原币种、价格版本、汇率、费用确定性 |
| 评测 | 原始预测、规范化预测、标准答案、各层级正确性，或生成图片路径、硬约束与人工分数 |

原始机器记录建议使用 JSONL；面向查看输出 CSV 和 HTML 对比报告，之后有需要再导出 Excel。不同渠道对同名模型的服务和定价可能不同，排名身份应至少包含“渠道 + 型号 + 参数档位”。

需要内置的执行机制：

1. 本地预检检查样本文件、支持的任务、价格规则和必要配置；有凭证后每个候选做 1 次最小远程验证，费用计入预检批次。
2. 每张图独立请求，默认不带历史对话，不把其他样本的结果传给当前样本。
3. 固定图片预处理规则、候选目录、输出结构与提示词版本。思考档位、输出上限、质量档位显式记录；跨厂商同名档位并不代表等量算力。
4. 交错模型运行顺序，固定低并发做基础时延测试；吞吐/并发测试另开批次，避免把本地排队时间当作模型速度。
5. 有限重试并逐次留痕。生图遇到无法确认结果的超时先尝试查回任务（接口支持时），不能无上限重发。
6. 逐条落盘、断点续跑；续跑匹配数据、模型、参数和提示词版本，防止误用旧结果。
7. 预算在发请求前检查并为在途请求预留，估算不完整时用保守上界；仅在收到响应后检查，不能严格控制开销。
8. 汇总同时展示失败数、缺失用量数、费用未知数、重复次数及样本数。保留总耗时与纯请求耗时，图片下载也单独记录。

首轮关闭联网搜索和额外工具，单独测试图像理解与生成。需要检索增强时另设产品工作流评测，计入额外调用成本。

## 9. 第一轮执行规模建议

1. **先整理真值**：核对现有 10 个真实照片素材，明确哪些能判断到大类、小类或品种；从已有素材和原图中补充，目标为 30—50 张真实照片，覆盖 10—15 个易混或常用类别。现有数量不足时先报告小样本，不用生成图凑数。
2. **识花预检**：9 个可识图候选每个 1 次最小调用，确认权限、图片传入、结构化输出与 usage 可读性。
3. **识花初筛**：若有 30 张合格样本，9 模型各跑一次为 270 次请求。开放识别与库内匹配分别跑则为 540 次；这些不是 270 次就覆盖的同一任务。预检和重试另计。
4. **识花复测**：对领先模型和难例重复 3 次，补足独立照片后再判断稳定排名；小样本差距需要附样本数和不确定性，不能过度解释。
5. **生图试点**：先以 Flash、Flare、Nano Banana 2.1 作为三家代表验证 7 图流程。这是接入试点选择，不是效果排名。其余 6 个候选保留在配置中。
6. **生图比较**：明确尺寸组后，为每个参与模型安排相同的 10 个案例，每例 3 次。三个模型、单一输入方案为 90 次；A/B/C 三组全跑为 270 次。每个案例记录花材、瓶器、场景及合格标准。
7. **最后测试串联**：把识别输出接入生图，记录完整工作流的正确性、耗时和费用，并与人工真值驱动生图对照。

第一版的具体交付应为：配置示例、经复核的样本清单、可运行的识花评测命令、逐次用量与费用记录、汇总报告和错误样本列表。生图可复用执行和计费框架，再增加图片保存与盲评。

当前已实现第一版可配置识花脚本、自动评分与离线测试；生图调用、库内候选匹配、并发/重复测试调度、自动重试、断点续跑、严格金额预算及账单对账仍在路线中。没有运行真实模型评测，也没有根据营销定位给出花材效果排名。
